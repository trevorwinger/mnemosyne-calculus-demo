Build a course tutoring web application with persistent student memory and an elegant interface. Treat this brief as an implementation request: inspect the repository, implement the application, run checks, and document how to launch it. Use the working name “Office Hours.” Use CSCI-201 Introduction to Programming in Java as the demo course. Instructors must be able to create their own courses in any subject; course content, concepts, prompts, and interface labels must not depend on the Java demo. Make routine implementation decisions without asking for approval; document assumptions. Do not publish or deploy externally as part of this task.

Provide two explicit entry paths: “I am an instructor” and “I am a student.” Present these as two restrained, accessible choices on the welcome screen, with a short description and one primary action each. Instructor entry leads to course creation and material management; student entry leads to joining a course and tutoring. Role selection expresses intent, not authorization. Keep roles attached to course memberships, support a person who teaches one course and studies in another, and provide a workspace switcher for users with both roles. Route returning users to their last authorized workspace.

Implement the instructor path from signup through a usable course. An instructor creates a course with title, optional course code, description, term, learning objectives, and tutoring preferences. Course creation assigns that user ownership of that new course only. Provide a setup flow: course details, upload materials, review processed content, and publish enrollment access. Save drafts between steps and allow later edits. Instructors can organize materials into modules or weeks, assign material types such as syllabus, lecture, reading, assignment, and answer key, and set student visibility and release dates. Default new uploads to draft. Show a course-readiness summary with actionable processing failures; allow publishing when at least one student-visible resource is ready, or an explicit instructor acknowledgment that the tutor will operate without course sources. Generate revocable, expiring enrollment links or codes and allow rotation, closing enrollment, archiving a course, and managing the roster. Do not automatically email invitations.

Implement the student path from signup through the first tutoring session. Students join through an enrollment link or code, confirm the course identity, and see a brief explanation of memory and instructor-visible progress. Prevent duplicate memberships and handle invalid, expired, revoked, or closed invitations. Joining grants student membership only and never instructor access. After joining, show the course overview, released materials, and actions to ask a question, practice a concept, or continue a session. Students can switch among enrolled courses; chat history, memory, retrieval, and progress stay separate for each course. If no materials are available, explain that course-specific sources are not yet available. Students cannot create official course materials or modify course settings. Personal file uploads are outside the initial student flow.

Create a custom frontend rather than adapting Open WebUI. The interface should serve students and instructors, with learning progress integrated into the chat experience. Use Next.js with TypeScript, Tailwind CSS, accessible component primitives, and Lucide icons for the frontend. Use FastAPI, Pydantic, SQLAlchemy, Alembic, and PostgreSQL for the backend. Use JSONB for memory observations and model metadata, with relational columns for identities, course membership, concepts, and events. Use a PostgreSQL-backed job queue with leases and retries for ingestion and memory updates, so Redis is not required initially. Verify current dependency documentation during implementation and pin compatible versions in lockfiles.

Design the UI around black, white, and UW–Superior yellow. Use white #FFFFFF for the default canvas and surfaces, black #000000 for primary text and icons, and UW–Superior Yellowjacket yellow #FFD046 for highlights, selected states, active toggles, and primary-action emphasis. This yellow is listed by UW–Superior Athletics at https://uwsyellowjackets.com/sports/2011/11/9/GEN_1109112614.aspx (RGB 255/208/70, Pantone 122). Use neutral grays only for secondary text, dividers, inactive controls, and surface hierarchy. Define these colors as shared design tokens across student and instructor workspaces. Remove the previous teal and warm off-white palette.

Use yellow sparingly so content remains the focus. Active toggles should have a yellow track with a black thumb or mark; inactive toggles should use grayscale styling. Include labels, thumb position, and accessible checked state so color is not the only indicator. Use black text and icons on yellow buttons and highlight fills, never white text on yellow or yellow body text on white. Give yellow controls a black boundary where required for contrast; use a black-and-white focus outline that stays visible against white, black, and yellow surfaces. Selected material chips, active navigation, and important annotations may use yellow with black text. Keep error and status distinctions understandable through text and icons within this palette. For code, use grayscale syntax styling and font emphasis, with yellow reserved for focused lines or instructional highlights.

Preserve generous spacing, thin borders, and shadows only where they establish hierarchy. Use a readable sans-serif typeface and a monospace typeface for code, with local fallbacks. Use a consistent spacing scale, 12–16 px corner radii, and short transitions that respect reduced-motion preferences. Avoid gradients, oversized marketing text, excessive cards, decorative charts, and badges that imply intelligence or certainty. Include a dark theme after the light theme works: black background, neutral dark surfaces, white text, and the same yellow accent with black text on yellow controls. Verify text contrast, focus visibility, and toggle states in both themes.

Make chat the primary student workspace. On desktop, provide a 240 px sidebar for course selection, a new-session action, recent sessions, Progress, and Memory. Use a centered conversation column around 760 px wide and an optional right panel for the current concept, suggested practice, and cited course sources. Keep the right panel collapsed by default. On mobile, replace the sidebar and context panel with drawers and keep the composer accessible above the keyboard. The composer needs multiline input, Enter to send, Shift+Enter for a newline, a send button, and a stop action during generation. Place material selection, model selection, and memory state in a compact toolbar that remains usable on mobile. Render Markdown, math when present, and syntax-highlighted Java with a copy button. Do not execute student code in this version.

Give the student home screen a concise welcome, a “Continue studying” action, and no more than three practice suggestions grounded in recorded learning events. An empty account should invite the student to choose a topic or paste a question. Suggestions must explain their basis, such as “You used a hint on array bounds last session.” Provide loading, empty, error, offline, and retry states. Preserve draft text after a failed request. Support keyboard navigation, visible focus, screen-reader labels, and chat announcements that do not read every streamed token. Verify layouts at 390, 768, and 1440 px widths, including long code blocks and long conversation titles.

Implement authentication and course-scoped authorization before connecting real student data. Use an established authentication library or OIDC integration with a documented local development flow; do not invent a password or token scheme. Keep demo identities behind an explicit development-only configuration that cannot be enabled in production. Support student and instructor roles, with instructor rights scoped to assigned courses. Resolve the student identity from the authenticated session; never accept a client-supplied student ID as authorization. Check ownership and enrollment for every session, message, source, memory, export, and progress endpoint. Keep provider credentials server-side. Include request-size limits, rate limits, secure cookie settings where applicable, and sanitized Markdown rendering.

Model users, courses, memberships, concepts, sessions, messages, exercises, attempts, learning events, memory items, concept summaries, source documents, source chunks, background jobs, and model runs. Use foreign keys, timestamps, uniqueness constraints, migrations, and indexes that match access patterns. Keep chat messages and learning events as separate records rather than one growing JSON document. Store source document versions and citation locations. Store prompt version, model identifier, latency, token usage when available, and status for model runs; avoid logging message contents or secrets by default. Make concept summaries reproducible from their underlying events.

Build memory around evidence of learning. Each learning event should identify the student, course, concept, source message or attempt, observed behavior, result, hint count, independence level, and date. Separate student self-report, tutor inference, and demonstrated performance. A useful observation is “Used i <= values.length, then corrected it after one hint”; avoid permanent labels such as “bad at arrays.” Use JSONB for details whose fields vary by activity. Distinguish lack of evidence from evidence of difficulty. Keep a compact summary per student and concept, with a recent evidence count and a status such as “Not assessed,” “Needs practice,” “Practicing,” or “Demonstrated independently.” Do not display uncalibrated mastery percentages.

Process memory updates asynchronously after an assessable student response or completed exercise. The model should propose a schema-validated observation, including references to the evidence; the backend validates reference ownership and writes the event. Do not treat an assistant explanation, a copied answer, or a student’s agreement as independent success. Do not write a learning event for every casual message. Use idempotency keys so retries and regenerated responses cannot duplicate progress. Serialize or version updates to each concept summary to prevent concurrent sessions from overwriting one another. Failed memory jobs must remain retryable and must not prevent the chat response from completing.

Make memory visible and controllable. Show students a Memory page with observations, evidence links, dates, and whether each item was self-reported or inferred. Allow correction, forgetting an item, clearing derived memory, and exporting their own data. Define the distinction between clearing memory and deleting chat history in plain language. A forgotten item must be removed from derived summaries and retrieval results; prevent old retained messages from automatically recreating it during later backfills. Use exclusion markers and a memory-reset timestamp where appropriate. When a student deletes source history, delete or rebuild dependent memory and indexes. Provide an export of the student’s own data. Retention should be configurable and documented.

Implement a tutoring harness as backend orchestration, not only a system prompt. Its goal is to guide and educate students rather than supply answers to their current tasks. Maintain an instructional state for each exercise: establish the goal, elicit an attempt, diagnose the difficulty, provide a graduated hint, ask for another attempt, and check transfer with a related problem. Allow explanations and analogous worked examples, but do not generate a submission-ready solution or final answer to the active exercise. Do not force a student to attempt a problem before answering a conceptual question. Give one manageable next step at a time and acknowledge uncertainty. Offer “Explain,” “Give me a hint,” and “Practice this” actions; do not offer a “Solve for me” bypass. Every selected model must pass through the same harness.

Implement the harness as a versioned policy plus structured planning, context assembly, response generation, and validation. Validate the proposed instructional action against the current exercise state and course rules before generation. Inspect the candidate response for complete solutions, unsupported citations, and contradictions with the allowed action. Buffer the candidate until checks complete; do not stream unchecked tokens and then attempt to retract a leaked answer. Show honest “Preparing guidance” and “Checking guidance” states during this delay, and deliver the checked response without pretending it is live model generation. On failure, regenerate with a bounded retry count, then return a bounded generic hint or clarification question. Use deterministic checks where possible and an administrator-configured local evaluator where useful. Do not claim any model-based gate guarantees zero answer leakage. Keep the evaluator and structured memory model configurable separately from the student's chat model. Never expose internal reasoning traces or unchecked drafts.

Evaluate tutoring behavior before enabling a model for students. Include requests for final answers, role-play bypasses, pasted assignment instructions, multi-turn attempts to accumulate the whole solution, student mistakes, genuine conceptual questions, and malicious instructions inside retrieved material. Check both solution leakage and over-refusal; useful explanations should remain possible. Record model digest, harness version, evaluation results, and limitations. Instructors can configure course prerequisites and pedagogical preferences, but students cannot disable the harness by changing models, sources, memory settings, or prompts. Keep grading and final academic judgments outside this application.

Add a course-material selector to every chat. Students can choose one or several released documents, a module/week, or “All released course materials.” Show selected sources as removable chips near the composer, with a searchable picker and document previews. Persist the choice for the chat and snapshot it for each request. Restrict retrieval to the intersection of this selection and current access permissions before ranking, including downstream query expansion and citation access. If the selection has no relevant evidence, say so; do not silently broaden to other materials. Offer an explicit action to broaden the selection. Changes apply to future requests and appear as a small event in the thread. Explain that prior replies may refer to earlier sources; offer a new chat for a clean source context. A selected document that becomes unavailable must be removed from future context with a visible notice. Recheck permissions on every turn, including historical retrieved excerpts and summaries; do not reuse revoked source content through a cache.

Add a per-chat “Use stored memory” toggle beside the material and model controls. This controls reads of cross-session student memory, not the ongoing conversation history or saving new learning evidence. When off, exclude stored memories, cross-session summaries, memory-retrieval tools, and memory-derived suggestions from all response-generation stages, including planners and evaluators. Keep the current conversation available. Memory-update workers may read existing records to maintain summaries, but must not pass those records to the response-generation pipeline when memory use is off. Explain that earlier replies may already reflect memory, and offer a fresh chat with memory use off when an uncontaminated context is wanted.

Save learning automatically for every eligible tutoring interaction. This is a mandatory application invariant, not an overridable default. Remove the “Save learning from this chat” toggle and any student, instructor, course, or administrator setting that disables collection. Do not implement a global collection opt-out. Enforce mandatory saving in the backend and job workers, not just the UI. Reject saving-disabled flags in API requests and imported session configurations. Snapshot the memory-use choice per request; disabling memory use must never suppress eligible learning jobs or progress updates. Preserve evidence validation, idempotency, and retries. Mandatory saving does not mean inventing learning observations for casual messages or treating every message as demonstrated performance.

Explain mandatory collection during student onboarding and in the chat interface. Display a noninteractive status, “Learning progress is saved automatically,” with the explanation “Use stored memory controls personalization of replies. Turning it off does not stop this chat from updating your learning progress.” Do not present memory-use-off as a private or unsaved mode. Existing correction, forgetting, export, retention, and deletion controls remain available for stored records; they do not disable collection from future eligible interactions. Deletion and forgetting must still invalidate dependent pending jobs or prevent removed evidence from being recreated. Report failed learning updates accurately rather than claiming persistence before a write succeeds.
